## 2. workflow 在做什麼（我看 code 之後的理解）

evolve_v8 是一個「outer agent loop + inner self-repair loop」結構：

```
iter 0: best-of-N baseline（兩個溫度跑 baseline 兩次，每題取最好）
  ↓
iter k (k=1..iterations):
  for 每個還沒過的題目:
    1. reviewer 看 spec + testbench + 失敗 RTL + harness log
       → 給出兩個 hypothesis（primary、alternative）+ 各自 confidence
    2. 若兩個 hypothesis 的 confidence 都 < min_confidence (0.4)
       → 標記 skip_low_confidence、不浪費 modifier 樣本
    3. modifier best-of-M（M=3, T=0.25/0.40/0.55）：
       a. 給 modifier prompt（含 spec、testbench、原 RTL、診斷）
       b. 拿到候選 RTL 之後本地 iverilog -tnull 檢查
       c. 若 parse 失敗，把錯誤丟回給 modifier 修語法（最多 inner_repair 次）
       d. 對每個候選打分數，header_changed / 沒碰 diagnosis 訊號 / 還在 parse fail 都會扣分
    4. 三個樣本都被擋下 → 退回 alternative hypothesis 重試一次 best-of-M
    5. 把當題最高分的「可提交」候選寫進 rtl，提交給 docker harness 重跑
  ↓
寫 evolution_history.json
```

關鍵的「為什麼 v8 跟 v7 不同」：v7 的 modifier 修不出有效 patch 的時候會直接放棄，v8 加了 `inner_repair`，讓同一個模型可以針對 iverilog 拋出來的 parse 錯誤去 self-repair。**但這次跑的 log 顯示 inner_repair_attempts 幾乎全等於 1**，代表大多數成功的 patch 第一次就 parse 過了；inner_repair 沒在解決真正卡關的問題。

## 3. 這次跑出來的失敗模式（log 裡實際看到的）

### 3.1 `header_changed` 是壓倒性的拒絕原因
跑下來目視大概有一半左右的 modifier 樣本被打 `score=3.0 reasons=['header_changed']`，例如：
- `cvdp_copilot_16qam_mapper_0001` primary 全 3.0 → fall back to alternative
- `cvdp_copilot_apb_dsp_unit_0001` primary 全 3.0 → fall back to alternative
- `cvdp_copilot_apb_history_shift_register_0001` primary 全 3.0 → fall back to alternative

prompt 裡明明寫得很清楚 `The file MUST begin with this EXACT module header`，模型還是會自作主張改 port type / 加 `signed` / 換 `output reg` ↔ `output logic`，導致 port-lock 檢查 reject。**這個失敗是 prompt-following 的問題，不是模型不會修 bug**。

### 3.2 `did_not_touch_diagnosis_signals`
有些樣本（例如 `car_parking_management_0001`）模型根本沒去碰 diagnosis 指出的訊號，只是改了周邊邏輯。

### 3.3 confidence=0.0 直接 skip
- iter 2 的 `apb_history_shift_register_0001` 兩個 hypothesis 都吐 `confidence=0.00`，被 min_confidence guard 跳過
- 同一題在 iter 1 也被 skip，代表 reviewer 對這題完全沒招

### 3.4 alternative 路徑很關鍵
log 顯示 iter 1 那次唯一的修好（`apb_dsp_unit_0001`）是走 alternative；如果只有 primary 沒有 alternative，這分就拿不到。**multi-hypothesis fallback 是現在 0.55 → 0.60 額外那 5–10 分的主要來源**。

## 4. 怎麼讓表現變好（具體行動方案，從容易到困難）

### 4.1 立刻可以做的（high ROI、不破壞 same-model anchor）

#### A. 程式化貼回 module header（消滅 header_changed）
**問題**：模型自由生成完整檔案 → header 被改 → 三個樣本全廢 → 浪費 best-of-M 額度。

**做法**：modifier 拿到回應後，先用 regex 把模型輸出的 `module ... endmodule` 抓出來，把 header（`module 名稱 #(...) (...) ;` 那一段）**強制換成**原檔案的 header，再做 iverilog parse。

**預期收益**：iter 1 那些被 `header_changed` 全拒的題目（`16qam_mapper_0001`、`apb_history_shift_register_0001` 等）直接從 `score=3.0` 提升到能進 sim 階段，**最樂觀情況下 pass rate 可能直接從 0.6 → 0.7+**，因為這些題目的 body fix 通常是對的，只是 header 被誤改。

**code 影響**：在 `evolve_v8.py` 的 `_score_candidate` 或 `_normalise_candidate` 加一個 pre-step，估計 < 30 行。

#### B. modifier 改成輸出 diff，而不是整個檔案
**問題**：要求模型重寫整個檔案 → 它自然會「順手優化」header 跟其他無關處。

**做法**：把 modifier system prompt 改成 unified diff 格式：
```
Output ONLY a unified diff (---/+++/@@) that applies cleanly with `patch -p0`.
Do NOT output any other content.
```
然後本地 `patch` 套上去。

**預期收益**：徹底解決 header rewriting，同時也保留所有不相關 logic（v8 的 `Preserve all unrelated logic verbatim` 約束會被自動滿足）。

**風險**：模型輸出 diff 的能力比輸出完整檔案弱，需要小幅微調 prompt 跟加一輪 retry on `patch` 失敗。

#### C. 把 inner_repair 預算挪去做 outer modifier samples
**證據**：log 裡所有成功的樣本都是 `inner_repair_attempts=1`（第一次 parse 就過），inner_repair 對結果幾乎零貢獻。

**做法**：`--inner-repair` 從 2 降到 1，把省下來的 token 預算花在 `--modifier-samples` 4 或 5（從 3 提到 4–5）。

**預期收益**：對「primary 三樣本都因為運氣不好被拒」的題目（這次 log 裡很多）有額外抽中機會。

#### D. iter 0 從 best-of-2 升 best-of-3
**證據**：iter 0 sample 0 (T=0.20) 過 6/20，sample 1 (T=0.55) 過 10/20 — 高溫度反而過更多，代表 baseline 對 N 很敏感。

**做法**：`--samples-iter0 3`，溫度 `0.2,0.55,0.85`。

**預期收益**：iter 0 baseline 從 0.50 提升到 0.55–0.60 是合理預期；後面 iter 1/2 的固定相對加成大概也會跟著高一點。

**代價**：iter 0 多花 1× dataset 的 docker sim 時間（這次大概多 2–3 分鐘）+ 一輪 baseline API 呼叫。

### 4.2 中度改造（需要小幅 refactor，但不換模型）

#### E. 失敗類別專用 prompt
log 裡的 root_cause 描述大致分三類：
1. **語法 / Icarus 不支援**（`var` 關鍵字、`$clog2` in port width、unpacked 陣列、dynamic part-select）
2. **時序 / FSM 邏輯**（state transition、backpressure、handshake）
3. **位寬 / 截斷 / signed-unsigned**（interpolation truncation、signed cast 漏掉）

**做法**：reviewer 多回一個 `bug_class: "syntax" | "fsm" | "width"`，modifier 根據 class 切換 system prompt，把「常見坑」直接寫在對應 class 的 prompt 裡（例如 syntax class 的 prompt 加一段「Icarus Verilog -g2012 限制：禁止 dynamic part-select on LHS、$clog2 不能放在 port width…」）。

**預期收益**：syntax 類失敗（這次很多）的修復率應該明顯改善，因為現在的 prompt 沒有把這些限制告訴模型。

#### F. 兩階段 modifier（patch + stitch）
**做法**：
- 第一階段：只請模型輸出「需要改的那幾行 `always_comb` 或 case 區塊」，不寫整個檔案
- 第二階段：本地用 AST/regex 把那些 block 替換進原檔，header / port / 其他 module 都不動

**預期收益**：徹底機械化保證除目標 block 外完全不變，比 prompt 約束強很多。

**代價**：要寫 SystemVerilog 區塊定位的 helper（用 `pyverilog` 或粗糙的 brace-matcher）。

#### G. 對「reviewer confidence < 0.4」的題目走第二意見
**證據**：iter 2 有一題被 confidence=0.00 直接 skip，全程沒給 modifier 機會 — 雖然合理，但少了一次出手。

**做法**：confidence 全低的時候，不直接 skip，而是換一個更具體的 prompt（例如「請用 cocotb assertion error 反推 expected vs actual signal trace」）再 review 一次；只有第二次也 < 0.4 才真 skip。

### 4.3 大改（會破壞 v8「same model 同價對比」的 anchor，但這是現實上要追分的方向）

#### H. reviewer 換成更強的推理模型，modifier 維持 qwen3.6
**理由**：log 裡 reviewer 的 root_cause 描述常常是泛泛的（「FSM next-state logic」、「Compilation failure」），但 modifier 接這種模糊診斷下手會打偏。換成 reasoning 模型（DeepSeek-R1、qwen3-max-reasoning、Claude Sonnet 等）寫 diagnosis，modifier 還是 qwen3.6 寫 patch — 這樣對「便宜模型能修多少 hardware bug」這個 thesis 還算公平，但能直接拉高診斷品質。

**注意**：要在 evolution_history 裡標清楚「reviewer-model = X、modifier-model = qwen3.6」，否則跟 baseline 比較會誤導。

#### I. modifier 的 best-of-M 改成樹狀 / MCTS
**做法**：不是平行抽 3 個獨立樣本，而是
- 抽 1 個樣本 → 評分
- 拿評分高的當「父節點」，再抽 2 個 variant（接著 modifier feedback「上一版分數 X，原因 Y」）
- 用 score 做 selection

**預期收益**：把 best-of-M 從「廣度優先」改「深度優先」，已有的好候選可以繼續 refine。

#### J. 自我蒸餾：把這次成功的 patch 拿去 fine-tune
**做法**：`work_evolve_v8_*` 累積的所有 `score=7.0` 候選 + 對應的 spec/testbench → SFT 一個 qwen3.6 的 LoRA。

**預期收益**：理論上 30-40 場 evolve run 之後，baseline pass rate 本身就會提升（不依賴 evolution loop）。

**代價**：fine-tune infra、SFT 資料的雜訊處理。

### 4.4 防禦性改進（這次踩到的雷）

#### K. 提前偵測 OpenRouter 額度
**問題**：這次第一次跑爆 key 額度後，openai SDK 預設 retry-on-403 把同一個 request 重打了 8 次，每次都 traceback，浪費時間 + 噴一堆 log。

**做法**：在 `_build_client` 啟動時打一個 1-token 的 `chat.completions.create`，回 403/402/429 就 fail-fast，立刻退出並提示「上 https://openrouter.ai/settings/keys 加額度」。

#### L. evolution_history.json 變成 incremental 寫
**問題**：v8 只在 `evolve_v8()` 結尾才寫一次 history。中途 crash（像這次 403）就完全沒 checkpoint，下次 resume 看不到部分進度。

**做法**：每跑完一個 iter 就寫一次 history（atomic：先寫 `.tmp`、再 `os.rename`）。

## 5. 我建議下一步怎麼做

如果你想最小工作量推進到 0.65+，依優先順序：

1. **做 A（程式化貼回 header）+ C（modifier-samples 4）+ D（samples-iter0 3）** — 大概 1–2 小時 code，預期能搶到 +2–4 題
2. **跑一次 cid003 full（不是 subset 20）做為新的 baseline anchor**，再決定要不要做 E / F
3. **做 K + L** 預防下次再被額度炸

如果想推到 0.7+：再做 E（class-specific prompt）跟 F（兩階段 modifier）。

如果要破 0.75+：開始考慮 H（混合模型 reviewer）。

## 5b. evolve_v9 實測結果（多 agent 版本）

把上面的 A（header normalizer）+ E（bug-class classifier agent）實作成 `evolve_v9.py`，跑同一個 cid003-20 一次。

### 結果：v9 = 11/20 (0.55)，比 v8 (12/20, 0.60) **差 1 題**

| Stage | v8 | v9 |
|---|---|---|
| iter 0 | 10/20 | 10/20 |
| iter 1 | 11/20（fixed `apb_dsp_unit_0001`，via alternative） | 11/20（fixed `car_parking_management_0001`，via primary） |
| iter 2 | **12/20**（fixed `axi_stream_upscale_0001`） | 11/20（無新增） |

v9 在 iter 1 修了一題不同的（v8 沒修到的），但 iter 2 反而沒修到 v8 那題。

### Postmortem

1. **Classifier JSON parse 失敗率 47%**：19 次呼叫，9 次回 `classifier_no_json` → 全部退到 `other`。最可能原因是 qwen3.6 reasoning mode 把答案寫到 `reasoning` 欄、`content=null`；加上 `max_tokens=120` 太緊。這些題目走的就是跟 v8 一樣的通用 prompt + 一輪浪費的 API。
2. **Class-specific prompt 是雙面刃**：當 classifier 把 `axi_stream_upscale_0001` 標成 `fsm`，modifier 拿到 backpressure checklist，但這題真正的修法跟 backpressure 沒關係 → patch 偏題 → 候選被 `last_attempt` 留下，iter 2 雖然 classifier 降級為 `other` 但 seed 已被汙染、沒辦法回頭。
3. **Header normalizer 只觸發 6 次**：有用，但這次 v9 run 本身 model 產出的 `header_changed` 比 v8 那次少很多（純隨機）。這個 lever 在這一場意義有限。
4. **單次 run 對比不夠**：iter 0 sample 0 v8 = 6/20、v9 = 8/20，同 prompt 同模型同 T 的差距就有 ±2；±1 題的 final 差距也可能純粹是抽樣噪音。

### v9.1 修法（沒再實際跑）

1. Classifier 拿不到 JSON 時，從 `reasoning` 欄位 fallback 一次
2. Classifier `max_tokens=120` → `max_tokens=400`
3. Classifier 結果信心 < 0.7 視為 `other`（寧可不加，也不誤導）
4. **正確的對比方法**：每個版本至少跑 3 個 seed，看分布而不是看單點

### 對 4 號方案表的更新

- **A（header normalizer）** 仍應該保留 — 沒造成壞處，且在 model 真的犯錯時是免費的救援
- **E（class-specific prompt）** 在 classifier 不可靠時 NET NEGATIVE — 先把 classifier 的 JSON parse 修穩才上
- **L（incremental history write）** 已在 v9 內順手實作（每個 iter 結束都 atomic 寫一次），這個改動單純是 win
